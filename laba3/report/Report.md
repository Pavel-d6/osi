# Лабораторная работа № 3

## 1. Цель работы

Приобретение практических навыков в управлении потоками в операционной системе и в обеспечении синхронизации между потоками.

## 2. Задание

Составить программу на языке Си, обрабатывающую данные в многопоточном режиме с использованием стандартных средств создания потоков операционной системы. Ограничение максимального количества потоков, работающих в один момент времени, задаётся ключом запуска программы. 

Вариант 6: произвести перемножение двух матриц, содержащих комплексные числа.

## 4. Описание алгоритма и распараллеливания

### 4.1 Представление данных

Комплексное число хранится структурой из двух полей типа `double`: вещественной части `re` и мнимой части `im`. Матрицы A (размер N×M), B (M×K) и результат C (N×K) хранятся одномерными массивами таких структур по строкам. Память под них выделяется с помощью `malloc`, поэтому размеры задаются при запуске программы. Элементы адресуются по формулам:

```
A[i][k] = A[i·M + k],   B[k][j] = B[k·K + j],   C[i][j] = C[i·K + j]
```

Входные матрицы заполняются псевдослучайными числами из диапазона от −1 до 1 для вещественной и мнимой частей. Начальное значение генератора фиксировано (`srand(1)`), поэтому при каждом запуске получаются одинаковые матрицы.

### 4.2 Алгоритм умножения

Элемент результирующей матрицы вычисляется как сумма произведений:

```
C[i][j] = Σ A[i][k] · B[k][j],   k = 0 … M − 1
```

Произведение комплексных чисел (a + bi)(c + di) имеет вещественную часть ac − bd и мнимую часть ad + bc. Сумма накапливается в локальных переменных и записывается в `C` один раз после завершения внутреннего цикла. Трудоёмкость алгоритма составляет O(N·M·K).

### 4.3 Распараллеливание

Для вычисления строки i матрицы C необходимы строка i матрицы A и вся матрица B. Поэтому строки результирующей матрицы делятся между потоками на непрерывные диапазоны: матрицы A и C делятся по строкам, а матрица B не делится и читается всеми потоками из общей памяти. Каждый поток записывает результат только в свои строки матрицы C.

Все параметры задания потока упакованы в структуру, указатель на которую передаётся в функцию потока:

```c
typedef struct {
    const Complex *A, *B;   // потоки только читают A и B
    Complex *C;             // и пишут только в свои строки C
    int M, K;               // A: N×M, B: M×K
    int row_begin;          // первая строка потока
    int row_end;            // конец диапазона, не включая
} Task;
```

У всех потоков одинаковые `A`, `B`, `C`, `M`, `K`; различаются только границы диапазона `row_begin` и `row_end`. Для p потоков и N строк каждому потоку достаётся N / p строк, а остаток от деления раздаётся первым потокам по одной строке. Таким образом, нагрузка потоков отличается не более чем на одну строку (например, при N = 10 и p = 4 потоки получают 3, 3, 2 и 2 строки).

Максимальное число потоков задаётся ключом запуска `-t`. Фактическое число создаваемых потоков равно `p = min(t, N)`, так как потоков больше, чем строк, создавать бессмысленно. Потоки создаются функцией `pthread_create`:

```c
int base = N / p, rest = N % p, row = 0;
for (int i = 0; i < p; i++) {
    int cnt = base + (i < rest ? 1 : 0);
    tasks[i] = (Task){ A, B, C, M, K, row, row + cnt };
    row += cnt;
    pthread_create(&tid[i], NULL, worker, &tasks[i]);
}
for (int i = 0; i < p; i++)
    pthread_join(tid[i], NULL);
```

### 4.4 Синхронизация

Диапазоны строк разных потоков не пересекаются, поэтому два потока никогда не записывают в одну и ту же ячейку матрицы C, а матрицы A и B только читаются. Гонок за данные нет, и мьютексы не требуются. Единственной точкой синхронизации является `pthread_join`: после его возврата для всех потоков результаты в матрице C гарантированно записаны.

Для корректной работы выполнены два условия. Массив заданий `tasks` создаётся заранее и существует до завершения потоков, так как потоки читают свои задания уже после выхода из цикла создания. Создание потоков и ожидание их завершения выполняются в разных циклах: если вызывать `pthread_join` сразу после `pthread_create`, потоки будут выполняться по очереди, и параллелизма не будет.

### 4.5 Запуск программы

```bash
gcc -O2 -pthread main.c -o main.o
./main.o -t 4 -n 1000
```

Ключ `-t` задаёт максимальное число потоков, ключ `-n` задаёт размер квадратных матриц N×N.

## 5. Методика исследования

Для оценки распараллеливания использовались три величины: время выполнения T(p), ускорение S(p) и эффективность E(p), где p — число потоков.

```
S(p) = T(1) / T(p),   E(p) = S(p) / p
```

Ускорение показывает, во сколько раз программа с p потоками работает быстрее, чем с одним потоком; в идеальном случае S(p) = p. Эффективность характеризует долю полезной работы, приходящуюся на один поток: E(p) = 1 соответствует идеальному использованию потоков, а значения меньше единицы указывают на потери из-за накладных расходов, конкуренции за ресурсы и ограниченного числа ядер.

Время измерялось внутри программы функцией `clock_gettime(CLOCK_MONOTONIC)`. В измеряемый интервал входят создание потоков, вычисления и ожидание завершения; генерация входных данных и выделение памяти в интервал не входят. Функция `clock()` не применялась, так как она суммирует процессорное время всех потоков и не отражает реального ускорения. За T(1) принято время работы этой же программы с одним потоком.

Исследование выполнено для квадратных матриц размером N = 200, 500, 1000 и 2000 и числа потоков p = 1, 2, 4, 8 и 16; для N = 2000 дополнительно измерен случай p = 30. Каждая точка измерялась три раза, в результаты заносилась медиана. Серия запусков выполнялась скриптом `bench.sh`, который вызывает программу при каждой комбинации параметров и вычисляет S и E.

## 6. Демонстрация числа потоков средствами ОС

Число потоков процесса наблюдалось командой `ps -M` (по одной строке на каждый поток) во время работы программы. Пример для запуска `./main.o -t 1 -n 2000`:

```
USER   PID   TT   %CPU STAT PRI   STIME   UTIME  COMMAND
pavel  20375 s000  0,0 S    31T   0:00.02 0:00.19 ./main.o -t 1 -n 2000
       20375        99,1 R    31T   0:00.02 0:02.95
```

Видны две строки с одним PID, то есть два потока одного процесса: главный и один рабочий. Главный поток находится в состоянии `S` (ожидание) с загрузкой 0,0 %: он вызвал `pthread_join` и ждёт завершения рабочего потока, а 0,19 с процессорного времени потратил на заполнение матриц до создания потоков. Рабочий поток находится в состоянии `R` (выполняется) и загружает ядро на 99,1 %; это и есть умножение матриц. Таким образом, при ключе `-t p` во время вычислений процесс содержит p + 1 поток.

**[Добавить скриншоты `ps -M` или `top -pid <PID> -stats pid,command,cpu,th` для `-t 4` и `-t 8`; ожидается 5 и 9 строк соответственно.]**

## 8. Анализ результатов

### 8.1 Масштабирование до четырёх потоков

Для матриц N = 200…1000 при p = 2 и p = 4 ускорение близко к идеальному: S = 1,85–2,01 и 3,77–3,95 соответственно, эффективность составляет 0,92–1,00 (табл. 1–3, рис. 1 и 2). Это объясняется устройством алгоритма: потоки обрабатывают непересекающиеся диапазоны строк, поэтому не блокируют друг друга и не ждут, а единственная синхронизация происходит в конце работы. Небольшие отклонения от идеала, в том числе значение S = 2,01 при N = 500 и p = 2, лежат в пределах погрешности измерений.

### 8.2 Насыщение при восьми потоках

При p = 8 ускорение составляет 4,95–5,82, а эффективность снижается до 0,62–0,73: дополнительные потоки перестают давать пропорциональный выигрыш. Вероятные причины:

- **Неоднородные ядра.** Процессор имеет 4 производительных и 4 энергоэффективных ядра. Совпадение границы «почти идеального» масштабирования (p ≤ 4) с числом производительных ядер говорит о том, что первые потоки получают быстрые ядра. Остальные потоки попадают на более медленные ядра. 
- **Конкуренция за кэш и память.** Все потоки читают общую матрицу B.


### 8.3 Число потоков больше числа ядер

Переход от 8 к 16 потокам выигрыша не даёт. При N = 200 и N = 500 ускорение практически не меняется (5,33 и 5,78), а эффективность падает почти вдвое (до 0,33–0,36). При N = 1000 время работы даже увеличивается (с 0,2933 до 0,3549 с), а ускорение снижается с 5,31 до 4,38. Когда потоков больше, чем ядер, операционная система вынуждена по очереди переключать потоки на одних и тех же ядрах. Каждое переключение контекста вытесняет данные потока из кэша, а на больших матрицах повторная загрузка данных обходится дороже (матрица B при N = 1000 занимает около 16 МБ). Дополнительных вычислительных ресурсов 16 потоков не получают, поэтому польза от них отсутствует, а накладные расходы остаются.

### 8.4 Влияние размера входных данных

При N = 200…1000 и p ≤ 4 размер матрицы слабо влияет на ускорение: эффективность при p = 4 равна 0,94, 0,99 и 0,94, то есть различия лежат в пределах погрешности.

При N = 2000 результат другой. Ускорение достигает лишь 1,59 при p = 4 и дальше не растёт: время при p = 4, 8, 16 и 30 практически одинаково (9,38–9,85 с), а эффективность уже при p = 2 равна 0,67 и при p = 4 равна 0,40. Добавление потоков перестаёт сокращать время, значит, ограничением становятся не вычисления, а общий ресурс, который потоки делят. Наиболее вероятная причина — память и кэш. Каждая матрица при N = 2000 занимает 64 МБ (при N = 1000 — 16 МБ) и не помещается в кэш процессора, а внутренний цикл читает B по столбцам с шагом 32 000 байт, то есть почти каждое обращение попадает в новую строку кэша. Программа становится ограниченной пропускной способностью памяти, а не вычислительной мощностью.

### 8.5 Проверка оценки трудоёмкости

Алгоритм имеет трудоёмкость O(N³). Время работы с одним потоком вырастает при переходе от N = 200 к N = 500 в 17,0 раза (по формуле (500/200)³ ≈ 15,6), от N = 500 к N = 1000 — в 8,3 раза (по формуле 2³ = 8), а от N = 1000 к N = 2000 — в 9,7 раза (ожидалось 8). Кубическая зависимость подтверждается; превышение на малых N объясняется короткой длительностью измеряемого интервала, а на N = 2000 — выходом данных за пределы кэша (п. 8.4).
